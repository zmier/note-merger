# MEETING_20260326_隐藏文件浏览与非索引

## 会议主题

在 Obsidian 中浏览和编辑以 `.` 开头的隐藏文件夹/文件，同时避免它们进入 Obsidian 的核心文件索引。

## 日期

2026-03-26

## 参会角色

- 用户
- Codex

## 用户需求整理

用户希望在 Obsidian 内部直接处理 vault 中的隐藏文件与隐藏目录，而不是每次切到系统文件管理器。

目标不是“让 Obsidian 完全接管所有隐藏文件”，而是更具体地希望实现下面这件事：

1. 能在 Obsidian 内浏览 `.开头` 的文件夹与文件。
2. 能直接在 Obsidian 内编辑这些文件。
3. 这些文件不要进入 Obsidian 的核心索引体系。

这里的“不要进入索引”，可理解为尽量避免进入以下核心能力：

- Search
- Graph View
- Backlinks / Unlinked mentions
- Quick Switcher 主结果
- Link suggestions
- Metadata cache 主索引流

## 用户背后的真实诉求

从工作流角度看，用户想解决的是“隐藏文件可操作性”和“知识库纯净度”之间的矛盾：

- 一方面，隐藏文件里经常放着很重要的配置、脚本、规则文件。
- 另一方面，这些文件通常不属于知识库正文，不希望它们污染搜索、图谱和链接建议。

换句话说，用户想要的是：

“可见、可改，但不参与知识管理索引。”

## 典型使用场景

- 编辑 `.obsidian` 内的配置、模板、snippets、插件辅助文件
- 编辑项目根目录中的 `.gitignore`、`.env.example`、`.cursor`、`.claude`、`.rules` 等文本文件
- 管理某些仅用于工具链的隐藏目录，但不希望它们被当成正式笔记纳入知识图谱

## 当前已知约束

### 1. Obsidian 原生对隐藏文件的支持有限

根据官方帮助文档，Obsidian 对隐藏文件夹的主流建议仍然是通过系统文件管理器访问，尤其是配置目录 `.obsidian` 这类路径。

这说明：

- Obsidian 原生文件浏览器并不是围绕“隐藏文件可视化管理”设计的
- 至少在官方文档层面，没有现成的“在文件树中完整管理隐藏文件”的标准工作流

### 2. `Excluded files` 不是“完全不索引”

官方帮助文档对 `Excluded files` 的说明是：

- 它们会从 Search、Graph View、Unlinked Mentions 中隐藏
- 在 Quick Switcher 和链接建议中被弱化或降权

但这不等于“这些文件完全不进入底层索引体系”，更不像是一个严格的“no-index”机制。

因此，如果直接依赖 `Excluded files`，只能做到“降低可见度”，不能保证“完全旁路索引”。

### 3. 插件 API 允许直接通过 adapter 访问 vault 路径

从当前插件环境可见，Obsidian 的 `DataAdapter` / `FileSystemAdapter` 提供了：

- `list(path)`
- `read(path)`
- `write(path)`
- `exists(path)`
- `stat(path)`

这意味着插件可以不依赖 `TFile` / `MetadataCache` 主流程，而是直接按路径读取和写入文件。

这为“插件自建隐藏文件浏览器/编辑器”提供了实现基础。

## 结论

可以实现，但要分清“哪一种实现”。

### 可行的实现

可行的是：

“由插件自己提供一套隐藏文件浏览与编辑界面，直接通过 adapter 访问隐藏路径，并尽量不把这些文件纳入 Obsidian 的主索引工作流。”

这条路线是现实且稳妥的。

### 不推荐或大概率不可行的实现

不推荐的是：

“让这些隐藏文件直接出现在 Obsidian 原生文件树和原生编辑器里，但同时又完全不参与核心索引。”

原因是：

- 原生文件树、索引、搜索、缓存是同一套核心系统的一部分
- 插件通过公开 API 很难优雅地把某一批文件从核心索引中彻底剥离
- 即便用内部 hack 勉强做到，也非常脆弱，后续升级风险高

## 我的看法

我认为这个需求非常合理，而且值得做。

但产品设计上应该明确转向：

“不要试图篡改 Obsidian 核心文件树，而是做一个插件级的旁路工作台。”

也就是说，这个功能最适合被设计成：

- 一个独立的 `Hidden Files` 视图
- 一个只处理文本类隐藏文件的浏览器 + 编辑器
- 一个与核心索引解耦的轻量工具面板

这样做的好处是：

- 功能边界清晰
- 不污染 Obsidian 核心行为
- 对主知识库索引影响最小
- 实现与维护风险可控

## 建议的产品方案

### V1 范围

建议第一版先支持：

- 浏览以 `.` 开头的文件和目录
- 只支持文本文件编辑
- 通过插件自定义 view 打开
- 不注册进 Markdown 文件流
- 不主动写入 metadata cache

建议优先支持的文本扩展名：

- `.md`
- `.txt`
- `.json`
- `.yaml`
- `.yml`
- `.toml`
- `.ini`
- `.css`
- `.js`
- `.ts`
- `.sh`

### V1 不建议做

- 二进制文件编辑
- 让隐藏文件混入原生 File Explorer
- 依赖 `Excluded files` 去模拟 no-index
- 接管 Obsidian 原生搜索结果

## 建议的架构思路

可以新增一个独立模块，例如：

```text
src/hidden-files/
  HiddenFilesManager.ts
  HiddenFilesView.ts
  HiddenFileEditorView.ts
  file-system.ts
  types.ts
```

核心思路：

1. 用 `app.vault.adapter.list()` 遍历指定根路径
2. 只展示 `.开头` 的目录和文件
3. 用插件自定义视图渲染树结构
4. 用插件自定义编辑器视图打开文本文件
5. 保存时走 `adapter.write()`，而不是 `vault.modify(TFile)`

这样可以尽量避开：

- `Vault.getMarkdownFiles()`
- `MetadataCache.getFileCache()`
- 基于 `TFile` 的主笔记流程

## 风险与注意事项

### 1. “完全 no-index” 需要谨慎表述

更准确的说法应是：

- “不进入插件主动使用的索引流”
- “不接入 Obsidian 正常的笔记工作流”

而不是承诺：

- “绝对不会被 Obsidian 内部任何缓存感知”

后者过于绝对，也不利于后续维护。

### 2. `.obsidian` 编辑是高风险操作

如果允许直接编辑 `.obsidian` 下的配置文件，需要提醒：

- 改动可能立即影响插件或主题行为
- 有些改动需要重载 Obsidian 才会生效
- 误改配置可能导致工作区异常

### 3. 桌面端优先

这类功能更适合桌面端优先交付。

如果后续考虑移动端，还要额外验证：

- adapter 行为差异
- 自定义编辑器体验
- 文件权限与刷新机制

## 当前建议结论

建议推进，但采用下面的定义：

“在 `note-merger` 中实现一个插件级隐藏文件浏览器/编辑器，用于管理 vault 内 `.开头` 的文本文件和目录，并尽量绕开 Obsidian 的主知识索引流，而不是改写原生文件树行为。”

这是我认为最稳、最实用、也最符合你真实需求的方案。

## 下一步建议

如果要继续推进，下一步最合适的是先写一份 PRD 和架构方案，进一步明确：

1. 隐藏文件的范围到底是“所有 dotfiles”还是重点支持 `.obsidian`
2. 是否只做文本文件
3. 是否要支持新建、删除、重命名
4. 是否要支持“收藏常用隐藏路径”
5. 是否要支持只读模式和风险提示
